## 1. 모바일 앱 라이브러리

### react-native-audio-api

**한 줄 설명:** 터치하면 즉시 소리가 나게 해주는 오디오 재생 + 믹싱 라이브러리.

**왜 쓰나?**
악기 앱에서 가장 중요한 건 터치와 소리 사이의 시간 차이(레이턴시)를 최소화하는 것이다. 일반적인 오디오 라이브러리는 터치할 때마다 파일을 열고 읽는 방식이라 50~200ms가 걸린다. 반면 이 라이브러리는 앱 시작 시 모든 WAV 샘플을 메모리에 미리 올려두기 때문에 10ms 이하로 즉시 재생이 가능하다.

> **레이턴시란?** 손가락이 화면에 닿는 순간부터 스피커에서 소리가 나오는 순간까지의 시간. 30ms를 넘으면 사람이 느끼기 시작하고, 100ms 이상이면 탭과 소리가 따로 노는 느낌이 들어 악기 연주가 불가능해진다.

**핵심 개념: 노드 그래프**
소리가 나는 과정을 물이 파이프를 타고 흐르는 것처럼 생각하면 된다. 샘플(WAV) → 볼륨 조절(GainNode) → 스피커 순서로 연결되고, 여러 트랙을 병렬로 연결하면 멀티트랙 믹싱이 된다.

**담당 역할**
- 가야금 현 탭 → 즉시 WAV 샘플 재생
- 멀티트랙 동시 재생 및 볼륨 조절
- `AudioContext.currentTime`으로 트랙 간 타이밍 동기화

---

### react-native-audio-recorder-player

**한 줄 설명:** 마이크로 소리를 녹음하고 파일로 저장하는 라이브러리.

**왜 쓰나?**
`react-native-audio-api`가 재생과 믹싱을 담당한다면, 이 라이브러리는 녹음만 전담한다. 사용자가 가야금을 연주하면 그 소리를 AAC 파일로 저장하고 경로를 반환한다. 이 파일을 서버에 업로드하거나 다시 불러와 다른 트랙과 합칠 수 있다.

**주의할 점**
두 라이브러리가 동시에 마이크/스피커를 잡으려 하면 iOS에서 충돌이 날 수 있다. 녹음 시작 전 재생을 잠깐 멈추거나, 오디오 세션을 "재생 + 녹음 동시 모드"로 설정해서 해결한다.

**담당 역할**
- 사용자 연주 소리 녹음
- AAC 포맷으로 저장 후 파일 경로 반환
- 저장된 파일을 서버로 업로드

---

### react-native-skia

**한 줄 설명:** 가야금, 장구, 대금 같은 악기 일러스트를 직접 그려주는 UI 렌더링 라이브러리.

**왜 쓰나?**
일반 React Native 컴포넌트(View, Image)로는 가야금 12현처럼 세밀한 커스텀 인터랙션을 만들기 어렵다. Skia는 그래픽 엔진 수준에서 직접 도형과 선을 그리기 때문에 현의 진동 효과, 탭 위치 감지 등을 정밀하게 구현할 수 있다.

**담당 역할**
- 가야금 12현, 장구 양면, 대금 음공 일러스트 렌더링
- 터치 위치에 따라 어떤 현/음공을 눌렀는지 판별

---

### react-native-reanimated

**한 줄 설명:** 현 진동, 장구 리바운드 같은 애니메이션을 부드럽게 만들어주는 라이브러리.

**왜 쓰나?**
일반 React Native 애니메이션은 JavaScript 스레드에서 실행되어 끊기거나 느려질 수 있다. Reanimated는 UI 스레드에서 직접 애니메이션을 실행해서 60fps를 안정적으로 유지한다.

**담당 역할**
- 가야금 현 탭 시 진동 효과
- 장구 탭 시 리바운드 효과
- 대금 음공 탭 시 호흡 파동 효과

---

### Zustand

**한 줄 설명:** 앱 전체에서 공유하는 상태(데이터)를 관리하는 라이브러리.

**왜 쓰나?**
멀티트랙 믹서에서 트랙 목록, 각 트랙의 볼륨, 음소거 여부 같은 정보를 여러 화면이 동시에 알아야 한다. Zustand는 이런 공유 데이터를 한 곳에서 관리하고 어느 화면에서든 바로 접근할 수 있게 해준다. Redux보다 코드가 훨씬 단순하다.

**담당 역할**
- 트랙 목록, 볼륨, 음소거 상태 관리
- 로그인한 유저 정보 관리
- 현재 선택된 악기, BPM 등 전역 설정 관리

---

### react-i18next / Google 번역 API

**한 줄 설명:** 앱을 한국어/영어로 전환해주는 다국어 처리.

**두 가지를 함께 쓰는 이유**

| | react-i18next | Google 번역 API |
|---|---|---|
| 대상 | 버튼, 메뉴 등 고정 텍스트 | Claude API 피드백 등 동적 텍스트 |
| 방식 | JSON 파일에 미리 번역 저장 | 실시간 API 호출로 번역 |
| 품질 | 직접 작성하니까 정확 | 자동번역 (국악 용어 주의) |
| 오프라인 | 가능 | 불가 |

"장구", "평조" 같은 국악 용어는 자동번역이 틀릴 수 있어서, UI의 고정 텍스트는 직접 작성한 JSON으로 관리하고 AI가 생성한 피드백 같은 동적 텍스트만 Google 번역 API를 사용한다.

### Google Sign-In SDK

**한 줄 설명:** Firebase 없이 Google 계정으로 로그인하게 해주는 라이브러리.

**흐름 요약**
앱에서 Google 로그인 버튼을 누르면 Google 계정 선택 화면이 뜨고, 로그인 완료 시 "ID 토큰"이라는 암호화된 인증 정보를 받는다. 이 토큰을 서버로 보내면 서버가 Google에 검증 요청을 해서 진짜 Google 유저인지 확인한다. Firebase Auth 없이도 이 과정이 가능하다.

**담당 역할**
- Google 로그인 UI 제공
- 로그인 성공 시 ID 토큰 발급
- 이후 모든 API 요청에 이 토큰을 헤더에 포함해서 전송

## 2. 백엔드 라이브러리

### FastAPI

**한 줄 설명:** Python으로 REST API 서버를 만드는 웹 프레임워크.

**왜 쓰나?**
Python 기반이라 librosa, numpy, scikit-learn 같은 데이터 분석 라이브러리를 그대로 같은 서버에서 쓸 수 있다. 비동기 처리를 기본으로 지원해서 여러 요청이 동시에 와도 빠르게 응답한다. API 문서도 자동으로 생성된다(`/docs` 경로).

**담당 역할**
- 앱의 모든 API 요청 처리
- Google ID 토큰 검증 미들웨어
- 오디오 파일 정적 서빙(`/static/audio/`)

---

### SQLAlchemy + MySQL

**한 줄 설명:** Python에서 MySQL 데이터베이스를 다루는 ORM(Object Relational Mapper).

**ORM이란?**
SQL 쿼리를 문자열로 직접 작성하지 않고 Python 클래스와 메서드로 DB를 다룰 수 있게 해주는 도구. 예를 들어 `SELECT * FROM tracks WHERE song_id = ?` 대신 `db.query(Track).filter(Track.song_id == song_id).all()` 형태로 쓴다.

**담당 역할**
- 유저, 곡, 트랙 메타데이터 저장 및 조회
- 오디오 파일 경로(audio_path) 관리
- 파일 크기 정보 저장 (10MB 제한 체크용)

---

### google-auth

**한 줄 설명:** 앱에서 받은 Google ID 토큰이 진짜인지 서버에서 검증하는 라이브러리.

**왜 필요한가?**
앱이 Google 로그인 후 받은 ID 토큰은 그냥 믿으면 안 된다. 누군가가 가짜 토큰을 만들어 보낼 수 있기 때문이다. `google-auth`는 이 토큰을 Google 서버에 확인 요청해서 진짜 Google 유저가 발급한 토큰인지 검증하고, 검증 성공 시 user_id(Google UID)를 추출한다.

**담당 역할**
- 모든 API 요청의 Google ID 토큰 검증
- 검증 성공 시 user_id 추출해서 이후 로직에 전달
- 토큰 만료/위조 시 401 에러 반환

---

### librosa

**한 줄 설명:** 오디오 파일을 분석해서 음악적 특징을 뽑아내는 Python 라이브러리.

**이 프로젝트에서 두 가지로 사용**

첫 번째, Markov Chain 학습 파이프라인에서 국악 WAV 파일의 온셋(소리가 시작되는 지점)을 자동으로 검출한다. 합주 음원을 librosa로 분석하면 각 악기 타격이 몇 초에 발생했는지 타임스탬프 배열로 나온다.

두 번째, 사용자 연주 분석에서 IOI(Inter-Onset Interval, 음 간 간격)를 계산한다. 예를 들어 0ms, 750ms, 1500ms 순서로 탭했다면 간격이 750ms, 750ms로 일정한 리듬이고, 이를 장단 기준 패턴과 비교해서 어떤 장단인지 판별한다.

**담당 역할**
- 국악 합주 음원에서 타격 타임스탬프 추출 (학습용)
- 사용자 연주 IOI 계산 (장단 매칭용)

---

### numpy / scikit-learn-extra

**한 줄 설명:** 수치 계산과 머신러닝 알고리즘을 제공하는 Python 라이브러리.

**numpy**
Markov Chain의 전이 행렬 자체가 numpy 2차원 배열이다. 행이 현재 패턴, 열이 다음 패턴, 값이 전이 확률을 나타낸다. 전이 확률 계산(MLE), 행렬 연산 모두 numpy로 처리한다. `.pkl` 파일로 저장되는 내용도 사실상 numpy 배열이다.

**scikit-learn-extra**
Markov Chain 학습 파이프라인의 패턴 클러스터링 단계에서 k-medoids 알고리즘을 제공한다. 국악 음원에서 추출한 수백 개의 패턴 조각들을 비슷한 것끼리 묶어서 패턴 ID를 부여하는 작업이다. 기본 scikit-learn에는 k-medoids가 없어서 `scikit-learn-extra`를 추가로 설치한다.

**담당 역할**
- 전이 행렬 생성 및 연산 (numpy)
- 패턴 클러스터링으로 패턴 DB 구성 (scikit-learn-extra)

---

### dtaidistance

**한 줄 설명:** DTW(Dynamic Time Warping) 거리를 빠르게 계산해주는 라이브러리.

**DTW란?**
두 리듬 패턴이 얼마나 비슷한지 측정하는 알고리즘. 일반적인 거리 비교는 같은 위치의 값만 비교하지만, DTW는 패턴이 약간 늘어나거나 줄어들어도 유사성을 인식한다. 사람이 박자를 완전히 일정하게 치기 어렵기 때문에 이 유연성이 중요하다.

**왜 이 라이브러리인가?**
Python에도 DTW 구현이 여러 개 있는데, `dtaidistance`는 C언어로 구현되어 있어서 순수 Python 구현보다 10~100배 빠르다. 장단 8종을 전부 비교해야 하기 때문에 속도가 중요하다.

**담당 역할**
- 사용자 연주 리듬 패턴과 장단 8종 기준 패턴의 유사도 계산
- 가장 거리가 짧은 장단을 매칭 결과로 반환

## 3. AI 모델 및 알고리즘

### Markov Chain — 반주 생성

**개념**
현재 상태만 보고 다음 상태를 확률적으로 결정하는 모델. "지금 패턴 A가 연주되고 있을 때 다음에 패턴 B가 나올 확률이 얼마인가"를 국악 데이터에서 학습한다.

**학습 과정**

```
국악 합주 음원 (WAV 파일)
        ↓
librosa로 온셋 검출 → 타격 타임스탬프 배열
        ↓
마디 단위로 자르기 → 패턴 조각들
        ↓
DTW 기반 k-medoids 클러스터링 → 비슷한 패턴끼리 묶어서 ID 부여
        ↓
음원별로 패턴 시퀀스 추출 (예: [3, 7, 12, 7, 3, 15, ...])
        ↓
조(key) × 장단 조합별로 전이 확률 계산
        ↓
.pkl 파일로 저장 → FastAPI 서버에 탑재
```

**반주 생성 과정**

```
사용자 연주 → 조 + 장단 감지
        ↓
해당 조합의 전이 행렬 로드 (예: 평조_중모리.pkl)
        ↓
시작 패턴 선택 (장단별 관용 시작 패턴 후보 리스트에서 선택)
        ↓
temperature 파라미터로 다양성 조절하면서 다음 패턴 순차 결정
        ↓
패턴 시퀀스 반환 → 앱에서 루프 샘플 조합해서 반주 오디오 생성
```

**핵심 파라미터**

| 파라미터 | 역할 |
|---|---|
| temperature | 0에 가까울수록 항상 같은 반주, 1에 가까울수록 매번 다른 반주 |
| seed_pattern | 반주 시작 패턴. 없으면 장단별 관용 시작 패턴 목록에서 랜덤 선택 |
| playbackRate | BPM 차이 보정. 사용자 BPM ÷ 기준 BPM. 0.5~2.0 범위로 클램핑 |
| 크로스페이드 | 루프 이음새 팝음 방지. 마디 길이의 3% 비율로 자동 계산 |

**장점**
- 모델 파일(.pkl)이 가볍고 추론 속도가 빠름
- 국악 실제 데이터에서 학습한 패턴이라 장단 문법에 맞는 반주 생성
- 공모전 어필 포인트: "공공데이터를 단순 재생이 아닌 AI 학습에 직접 활용"

**단점**
- 현재 패턴만 보고 결정하기 때문에 장기적인 음악 흐름(기승전결)을 만들지 못함
- 학습 데이터가 적은 조합(예: 계면조_엇모리)은 반주 품질이 낮아질 수 있음

### 코사인 유사도 — 조(Key) 감지

**개념**
두 벡터(숫자 배열)가 얼마나 같은 방향을 가리키는지 측정하는 방법. 1에 가까울수록 유사하고, 0에 가까울수록 다르다.

**이 프로젝트에서의 활용**
사용자가 연주한 음들의 히스토그램(어떤 음을 얼마나 많이 썼는지)을 평조 음계 템플릿, 계면조 음계 템플릿과 각각 비교해서 더 유사한 쪽을 조로 판별한다. 국악 음계는 5음 위주로 구성이 정해져 있어서 이 방식이 잘 맞는다.

**흐름**

```
사용자 연주 이벤트 (탭한 음 목록)
        ↓
음 히스토그램 생성 (옥타브 무시, 음계 클래스만)
        ↓
평조 템플릿과 코사인 유사도 계산
계면조 템플릿과 코사인 유사도 계산
        ↓
더 높은 쪽을 조로 판별 + 신뢰도 반환
```

**추가 학습 불필요**
평조/계면조의 구성음은 이미 국악 이론으로 알려진 지식이라 데이터 학습 없이 수동으로 템플릿을 작성해서 사용한다.

---

### DTW — 장단 매칭

**개념**
두 시계열(시간에 따라 변하는 값의 배열)이 얼마나 비슷한지 측정하는 알고리즘. 단순 비교와 달리 시간 축이 약간 늘어나거나 줄어들어도 유사도를 인식한다.

**이 프로젝트에서의 활용**
사용자의 타격 간격(IOI) 패턴과 장단 8종의 기준 IOI 패턴을 DTW로 비교해서 가장 가까운 장단을 찾는다. 예를 들어 중모리를 조금 빠르게 쳤어도 DTW는 패턴 모양을 보고 중모리로 인식한다.

**흐름**

```
사용자 타격 타임스탬프 (예: 0ms, 750ms, 1500ms, 2250ms ...)
        ↓
IOI 계산 (간격 배열: 750, 750, 750 ...)
        ↓
장단 8종 기준 IOI 패턴과 각각 DTW 거리 계산
        ↓
거리가 가장 짧은 장단을 매칭 결과로 반환
```

---

### Claude API — 텍스트 피드백

**개념**
반주 생성 자체에는 관여하지 않고, 사용자에게 보여줄 음악적 설명과 격려 텍스트를 생성하는 역할만 담당한다.

**사용 시점**

| 시점 | 내용 |
|---|---|
| 따라하기 완주 후 | 정확도 점수 기반 격려 멘트 + 틀린 부분 피드백 |
| 반주 생성 후 | 감지된 조와 장단이 어떤 느낌인지 설명 |

**흐름**

```
(따라하기 완주 시)
정확도 점수 + 감지된 조 + 곡 이름 + UI 언어 설정
        ↓
FastAPI → Claude API 호출 (프롬프트 전달)
        ↓
Claude가 국악 입문자 눈높이에 맞는 피드백 텍스트 생성
        ↓
앱 화면에 표시
```

## 4. 인증 흐름

Firebase 없이 Google 로그인을 구현하는 전체 흐름.

```
[앱]
사용자가 "Google로 로그인" 버튼 탭
        ↓
Google 계정 선택 화면 표시 (Google Sign-In SDK)
        ↓
로그인 완료 → Google ID 토큰 발급
        ↓
이후 모든 API 요청 헤더에 토큰 포함
Authorization: Bearer {Google ID Token}

[서버 - 모든 요청마다]
헤더에서 토큰 추출
        ↓
google-auth 라이브러리로 Google 서버에 검증 요청
        ↓
검증 성공 → user_id(Google UID) 추출
검증 실패 → 401 에러 반환 (만료, 위조 등)
        ↓
검증된 user_id를 각 API 로직으로 전달
```

**공개 경로 (토큰 없이 접근 가능)**
- `/` 루트
- `/docs` API 문서
- `/health` 서버 상태 확인

**보호 경로 (토큰 필수)**
- `/api/accompaniment` 반주 생성
- `/api/analyze` 연주 분석
- `/api/feedback` AI 피드백
- `/api/tracks/upload` 파일 업로드
- `/api/share` 공유 링크 생성

## 5. 전체 데이터 흐름 요약

### 자유 창작 모드 (가야금 연주 → 반주 추가)

```
가야금 현 탭
        ↓ (react-native-audio-api, <10ms)
WAV 샘플 즉시 재생 + 연주 이벤트 기록 (음, 타임스탬프)

        ↓
녹음 버튼 탭 → react-native-audio-recorder-player 녹음 시작
(AudioContext.currentTime으로 타임스탬프 기록)

        ↓
정지 버튼 → AAC 파일 저장 → 서버 업로드
POST /api/tracks/upload → /audio/{user_id}/track_{id}.aac

        ↓
AI 반주 생성 버튼 탭
POST /api/analyze → 조(평조) + 장단(중모리) 감지
POST /api/accompaniment → 패턴 시퀀스 반환

        ↓
패턴 시퀀스 → 루프 샘플 조합 → 크로스페이드(마디×3%)
→ 반주 트랙 생성 → 믹서에 추가

        ↓
볼륨 조절 후 저장 → POST /api/tracks/upload (믹스 파일)
→ Firestore에 song 메타데이터 저장
```

### 따라하기 모드 (아리랑 연주)

```
곡 선택 (아리랑) → 악기 선택 (가야금)
        ↓
악보 하이라이트 가이드 표시 (다음 칠 현 노란색 강조)

        ↓
사용자가 현 탭 → 타이밍 기록
기준 타이밍과 비교 (±200ms 이내 = 정확)
소비 처리: 한 번 쓴 이벤트는 재사용 안 함

        ↓
완주 후 정확도 계산
POST /api/feedback → Claude API
→ 피드백 텍스트 + 조/장단 설명 화면 표시

        ↓
SNS 공유 버튼 → POST /api/share → 단축 링크 생성
```
